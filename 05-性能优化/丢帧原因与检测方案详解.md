# 丢帧原因与检测方案详解

## 问题

> 丢帧一般是什么原因引起的？怎么检测丢帧？Choreographer.FrameCallback 和 Looper.Printer（BlockCanary）的原理分别是什么？

## 核心答案

丢帧的本质是一帧的处理时间超过了 VSYNC 周期（60Hz = 16.6ms）。常见原因：主线程耗时操作（IO/GC/锁等待）、布局层级过深、过度绘制、Binder 阻塞、系统降频。检测方案：Choreographer.FrameCallback 计算帧间隔判断丢帧数；Looper.Printer 监控主线程每个 Message 的处理耗时（BlockCanary 原理），超阈值则采样堆栈上报。前者只能知道丢了多少帧，后者能定位到具体哪个消息导致的卡顿。

## 深入解析

### 原理层（源码级）

**一帧的时间预算：**

```
60Hz 屏幕：16.6ms 一帧
90Hz 屏幕：11.1ms 一帧
120Hz 屏幕：8.3ms 一帧

一帧内要完成的事（主线程）：
  ① 处理输入事件 (CALLBACK_INPUT)
  ② 执行动画 (CALLBACK_ANIMATION)
  ③ View 三大流程 (CALLBACK_TRAVERSAL: measure → layout → draw)
  ④ 提交帧数据 (CALLBACK_COMMIT)

任何一个阶段超时 → 错过 VSYNC → 丢帧
```

**丢帧原因全景：**

```
丢帧原因
├── 主线程耗时（最常见）
│   ├── 主线程 IO（SharedPreferences.commit()、数据库查询、文件读写）
│   ├── 主线程网络请求
│   ├── 复杂计算（JSON 解析、大量数据处理）
│   ├── 频繁 GC（内存抖动 → STW 暂停主线程）
│   └── 锁等待（synchronized 阻塞、Binder 跨进程调用）
│
├── View 系统
│   ├── 布局层级过深（measure/layout 递归次数多）
│   ├── 过度绘制（同一像素多次绘制）
│   ├── requestLayout 过于频繁
│   └── 不必要的 invalidate
│
├── 渲染线程（RenderThread）
│   ├── DisplayList 构建耗时（View 树过于复杂）
│   ├── GPU 渲染超时（Shader 首次编译、大纹理）
│   └── 硬件加速回退软件渲染
│
└── 系统层面
    ├── CPU 调度（App 被降频、大核不可用）
    ├── 温控降频（thermal throttling）
    ├── 后台进程抢占资源
    └── Binder 调用阻塞（system_server 繁忙）
```

### 方案一：Choreographer.FrameCallback 详解

#### 原理

```
Choreographer 每次 VSYNC 到来时执行 doFrame()
→ 注册 FrameCallback，每次 doFrame 结束后回调
→ 在回调中比较相邻两次帧的时间差
→ 差值 > 16.6ms × N → 丢了 N 帧
```

#### 源码级实现

```kotlin
object FPSMonitor {
    private var lastFrameTimeNanos = 0L
    private var frameCount = 0
    private var droppedTotal = 0

    // Choreographer 源码中 doFrame 的回调顺序：
    // CALLBACK_INPUT → CALLBACK_ANIMATION → CALLBACK_TRAVERSAL → CALLBACK_COMMIT
    // FrameCallback 在 CALLBACK_COMMIT 之后执行，此时一帧已经完成
    private val frameCallback = object : Choreographer.FrameCallback {
        override fun doFrame(frameTimeNanos: Long) {
            if (lastFrameTimeNanos != 0L) {
                // frameTimeNanos 是本次 VSYNC 的目标时间（纳秒）
                // 两次帧之间的间隔
                val diffNanos = frameTimeNanos - lastFrameTimeNanos
                val diffMs = diffNanos / 1_000_000  // 转为毫秒

                // 计算丢帧数：间隔 / 16.6ms - 1
                val droppedFrames = (diffMs / 16.6).toInt() - 1

                if (droppedFrames > 0) {
                    droppedTotal += droppedFrames
                    onFrameDropped(droppedFrames, diffMs)
                }
            }
            lastFrameTimeNanos = frameTimeNanos
            frameCount++

            // 继续注册下一帧回调（持续监听）
            Choreographer.getInstance().postFrameCallback(this)
        }
    }

    fun start() {
        // postFrameCallback 注册一个在下一帧 doFrame 结束时执行的回调
        // 注意：不是立即执行，而是等 VSYNC 到来后执行
        Choreographer.getInstance().postFrameCallback(frameCallback)
    }

    fun stop() {
        Choreographer.getInstance().removeFrameCallback(frameCallback)
        lastFrameTimeNanos = 0L
    }

    private fun onFrameDropped(count: Int, costMs: Long) {
        when {
            count >= 42 -> reportFrozen(costMs)    // 冻帧 > 700ms
            count >= 6  -> reportJank(costMs)      // 严重卡顿 > 100ms
            count >= 3  -> reportSlightJank(costMs) // 轻微卡顿 > 50ms
        }
    }

    private fun reportFrozen(costMs: Long) {
        Log.e("FPS", "冻帧！丢帧 42+，耗时 ${costMs}ms")
        // 上报：此时通常伴随 ANR 风险
    }

    private fun reportJank(costMs: Long) {
        Log.w("FPS", "严重卡顿，丢帧 6+，耗时 ${costMs}ms")
    }

    private fun reportSlightJank(costMs: Long) {
        Log.i("FPS", "轻微卡顿，丢帧 3+，耗时 ${costMs}ms")
    }
}
```

#### Choreographer.doFrame 源码（理解回调时机）

```java
// Choreographer.java
void doFrame(long frameTimeNanos, int frame) {
    final long startNanos;
    synchronized (mLock) {
        long intendedFrameTimeNanos = frameTimeNanos;
        startNanos = System.nanoTime();

        // 计算掉帧数（系统日志 "Skipped XX frames" 就在这里打印）
        final long jitterNanos = startNanos - frameTimeNanos;
        if (jitterNanos >= mFrameIntervalNanos) {
            final long skippedFrames = jitterNanos / mFrameIntervalNanos;
            if (skippedFrames >= SKIPPED_FRAME_WARNING_LIMIT) {
                Log.i(TAG, "Skipped " + skippedFrames + " frames! "
                    + "The application may be doing too much work "
                    + "on its main thread.");
            }
        }
    }

    // 按顺序执行回调
    doCallbacks(Choreographer.CALLBACK_INPUT, frameTimeNanos);
    doCallbacks(Choreographer.CALLBACK_ANIMATION, frameTimeNanos);
    doCallbacks(Choreographer.CALLBACK_INSETS_ANIMATION, frameTimeNanos);
    doCallbacks(Choreographer.CALLBACK_TRAVERSAL, frameTimeNanos);
    doCallbacks(Choreographer.CALLBACK_COMMIT, frameTimeNanos);

    // FrameCallback 在 doFrame 最后执行
    // 所以 frameTimeNanos 反映的是"这一帧开始的时间"
    // 不是"这一帧完成的时间"
}
```

#### postFrameCallback 的注册原理

```java
// Choreographer.java
public void postFrameCallback(FrameCallback callback) {
    postFrameCallbackDelayed(callback, 0);
}

public void postFrameCallbackDelayed(FrameCallback callback, long delayMillis) {
    // 内部用 CALLBACK_ANIMATION 类型注册
    // 但执行时机是在 doFrame 的 COMMIT 阶段之后
    postCallbackDelayedInternal(CALLBACK_ANIMATION,
            callback, FRAME_CALLBACK_TOKEN, delayMillis);
}
```

#### 方案一的优缺点

```
优点：
  → 实现简单，几行代码
  → 性能开销极低（每帧只做一次时间比较）
  → 能精确知道丢了多少帧

缺点：
  → 只知道"丢了 N 帧"，不知道"为什么丢"
  → 不知道是哪个方法/消息导致的卡顿
  → 无法获取卡顿时的堆栈信息
  → 适合做监控报警，不适合做归因分析

适用场景：
  → 线上 FPS 监控
  → 卡顿报警（丢帧数超阈值触发）
  → 配合其他方案做归因
```

### 方案二：Looper.Printer（BlockCanary 原理）详解

#### 原理

```
Looper.loop() 中每次 dispatchMessage 前后都会打印日志：
  ">>>>> Dispatching to Handler ... "
  "<<<<< Finished to Handler ..."

利用 Looper.setMessageLogging() 设置自定义 Printer：
  → ">>>>>" 时记录开始时间，启动堆栈采样线程
  → "<<<<<" 时计算耗时
  → 超过阈值（默认 500ms）→ 上报卡顿信息 + 采样堆栈
```

#### Looper.loop() 源码中的打印位置

```java
// Looper.java
public static void loop() {
    final Looper me = myLooper();
    final MessageQueue queue = me.mQueue;

    for (;;) {
        Message msg = queue.next();
        if (msg == null) return;

        // ★ 打印点 1：消息处理前
        final Printer logging = me.mLogging;
        if (logging != null) {
            logging.println(">>>>> Dispatching to " + msg.target
                + " " + msg.callback + " what=" + msg.what);
        }

        // 实际分发消息
        msg.target.dispatchMessage(msg);

        // ★ 打印点 2：消息处理后
        if (logging != null) {
            logging.println("<<<<< Finished to " + msg.target
                + " " + msg.callback);
        }

        msg.recycleUnchecked();
    }
}
```

#### BlockCanary 完整实现

```kotlin
class BlockCanary {
    companion object {
        private const val TAG = "BlockCanary"
        private const val THRESHOLD_MS = 500L        // 卡顿阈值
        private const val SAMPLE_INTERVAL_MS = 50L   // 堆栈采样间隔
    }

    private val stackSampler = StackSampler(
        thread = Looper.getMainLooper().thread,
        intervalMs = SAMPLE_INTERVAL_MS
    )

    private var startTime = 0L
    private var startThreadTime = 0L

    // 核心：自定义 Printer
    private val printer = object : Printer {
        override fun println(x: String) {
            if (x.startsWith(">>>>> Dispatching")) {
                // ★ 消息处理开始
                onStart(x)
            } else if (x.startsWith("<<<<< Finished")) {
                // ★ 消息处理结束
                onEnd(x)
            }
        }
    }

    fun start() {
        // 设置 Looper 的 Printer
        Looper.getMainLooper().setMessageLogging(printer)
    }

    fun stop() {
        Looper.getMainLooper().setMessageLogging(null)
        stackSampler.stop()
    }

    private fun onStart(log: String) {
        // 记录开始时间
        startTime = System.currentTimeMillis()
        startThreadTime = SystemClock.currentThreadTimeMillis()

        // 启动堆栈采样线程
        // 每隔 50ms 采样一次主线程堆栈
        stackSampler.start()
    }

    private fun onEnd(log: String) {
        // 计算墙钟时间（包含 IO 等待、锁等待、CPU 执行）
        val wallTime = System.currentTimeMillis() - startTime

        // 计算 CPU 时间（实际在 CPU 上执行的时间）
        val cpuTime = SystemClock.currentThreadTimeMillis() - startThreadTime

        // 停止采样
        stackSampler.stop()

        if (wallTime > THRESHOLD_MS) {
            // 卡顿！收集信息
            val stacks = stackSampler.getStacks(startTime, System.currentTimeMillis())
            val cpuUsage = getProcessCpuUsage()
            val memoryInfo = getMemoryInfo()

            // 归因分析
            val cause = analyzeCause(wallTime, cpuTime)

            // 上报
            val info = JankInfo(
                wallTime = wallTime,
                cpuTime = cpuTime,
                cause = cause,
                stacks = stacks,
                cpuUsage = cpuUsage,
                memoryInfo = memoryInfo,
                message = log
            )
            Log.e(TAG, "检测到卡顿: ${info}")
            reportToServer(info)
        }
    }

    // ★ 归因分析：区分 CPU 密集 vs IO/锁等待
    private fun analyzeCause(wallTime: Long, cpuTime: Long): JankCause {
        val cpuRatio = cpuTime.toFloat() / wallTime
        return when {
            cpuRatio > 0.8f -> JankCause.CPU_INTENSIVE  // CPU 密集
            cpuRatio < 0.3f -> JankCause.IO_OR_LOCK      // IO 或锁等待
            else -> JankCause.MIXED                       // 混合
        }
    }
}
```

#### 堆栈采样器实现

```kotlin
class StackSampler(
    private val thread: Thread,        // 主线程
    private val intervalMs: Long       // 采样间隔 50ms
) {
    // 存储采样结果：时间戳 → 堆栈
    private val stackMap = LinkedHashMap<Long, String>()
    private var timer: Timer? = null

    fun start() {
        stackMap.clear()
        timer = Timer("StackSampler").apply {
            scheduleAtFixedRate(object : TimerTask() {
                override fun run() {
                    // ★ 在采样线程中获取主线程堆栈
                    // Thread.getStackTrace() 是线程安全的
                    // 但有一定性能开销（需要暂停目标线程瞬间）
                    val stack = thread.stackTrace
                        .filter { it.className.startsWith("com.example") } // 只保留业务代码
                        .joinToString("\n") { "\tat ${it.className}.${it.methodName}(${it.fileName}:${it.lineNumber})" }

                    synchronized(stackMap) {
                        stackMap[System.currentTimeMillis()] = stack
                    }
                }
            }, 0, intervalMs)
        }
    }

    fun stop() {
        timer?.cancel()
        timer = null
    }

    fun getStacks(startTime: Long, endTime: Long): List<String> {
        synchronized(stackMap) {
            return stackMap
                .filter { it.key in startTime..endTime }
                .values.toList()
        }
    }
}
```

#### 方案二的优缺点

```
优点：
  → 能精确定位到卡顿的方法和行号
  → 通过 wallTime vs cpuTime 区分卡顿类型
  → 堆栈采样开销可控（每 50ms 一次）
  → 适合线上监控

缺点：
  → 需要设置 Looper Printer（如果其他库也设置了会冲突）
  → 堆栈采样有轻微性能开销
  → 只能监控主线程 Message 粒度的卡顿
  → 阈值太高（500ms）可能漏掉轻微卡顿

适用场景：
  → 线上卡顿归因分析
  → 定位具体卡顿方法
  → 区分 CPU 密集型和 IO/锁等待型卡顿
```

### 方案一 vs 方案二 对比

| 维度 | Choreographer.FrameCallback | Looper.Printer (BlockCanary) |
|------|---------------------------|------------------------------|
| 监控粒度 | 帧级别（每帧回调） | 消息级别（每个 Message） |
| 能否知道丢帧数 | 能（精确到帧） | 不能（只知道消息耗时） |
| 能否定位卡顿方法 | 不能 | 能（堆栈采样） |
| 能否区分卡顿类型 | 不能 | 能（wallTime vs cpuTime） |
| 性能开销 | 极低（时间比较） | 低（50ms 采样一次堆栈） |
| 实现复杂度 | 简单（几行代码） | 中等（需要采样线程 + 归因逻辑） |
| 线上适用性 | 适合 | 适合 |
| 与其他库冲突风险 | 无 | 有（Looper Printer 只能设一个） |
| 监控范围 | 只能看整帧耗时 | 能看每个 Message 的耗时 |

**推荐组合使用：**

```
FrameCallback → 线上 FPS 监控 + 丢帧报警
Looper.Printer → 卡顿发生时归因分析
两者配合：
  FrameCallback 发现丢帧 → 触发 Looper.Printer 采集堆栈 → 定位卡顿方法
```

### 实战层（项目经验）

**VSYNC 机制：**

```
                    VSYNC 信号 (硬件中断)
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
    VSYNC-app      VSYNC-sf       Display 刷新
   (App 开始绘制)  (SF 开始合成)   (显示上一帧)

Triple Buffering:
  Frame N:   [CPU绘制] [GPU渲染]
  Frame N+1:          [CPU绘制] [GPU渲染]
  Display:                      [显示N] [显示N+1]
```

**GC 导致丢帧：**

```
内存抖动：
  短时间内大量创建临时对象
    → 触发 GC（垃圾回收）
    → GC 会 STW（Stop The World）暂停所有线程
    → 主线程暂停 5-10ms → 丢帧

典型场景：
  → onDraw 里 new 对象
  → 循环中字符串拼接
  → 频繁创建 List/Map
```

**Binder 阻塞导致丢帧：**

```
主线程调用系统服务（Binder 跨进程）
  → system_server 繁忙时主线程阻塞等待返回
  → 可能耗时 10-100ms → 丢帧

典型场景：
  → 主线程调用 PackageManager.getInstalledPackages()
  → 主线程调用 ContentResolver.query()
  → 主线程调用 ActivityManager.getRunningTasks()
```

## 记忆锚点

丢帧 = 一帧超过 16.6ms。原因四字诀：**IO 锁 GC 布局**（主线程 IO、锁等待、GC 停顿、布局过深）。检测两板斧：FrameCallback 算丢了几帧（快但粗），Looper.Printer 抓堆栈定位方法（慢但准）。两者配合：先报警再归因。
